# Remote offline-root ceremony with SmartCard-HSM public key authentication

| | |
|---|---|
| Status | Accepted; implementation on `feat/smartcard-hsm-remote-ceremony` |
| Date | 2026-11-15 |
| Scope | `sc-hsm-cloud` provider: RAM bridge, ceremony service, HSM API, HSM page, keyholder agent |
| Replaces | Remote assembly of the root key from DKEK shares read off custodian tokens (now "legacy share mode") |

## 1. Context

UCM can keep a root CA offline on a CardContact SmartCard-HSM. In-person key ceremonies are the norm (WebTrust, CA/B Forum audit practice), but here the keyholders are geographically dispersed and cannot meet for each ceremony. The requirement is a **remote** ceremony that comes as close as possible to an in-person one:

1. Each keyholder is shown to be who they claim to be, using a hardware-bound credential, at the time of the ceremony.
2. No secret (key, key share, DKEK, PIN) is disclosed to the UCM server, the network, or another keyholder.
3. An eavesdropper or active network attacker learns nothing reusable and cannot steer the ceremony unnoticed.
4. No single person, including a UCM administrator, can use the root key.
5. Every use of the root key is recorded in a form each keyholder can check independently.

## 2. Why the first implementation is retired

The first version of this branch rebuilt the root key in every window. It read DKEK shares from each custodian token over RAMOverHTTP and imported them into an "assembly" token. A review found that this design cannot meet requirement 2, whatever hardening is added:

* `IMPORT DKEK SHARE` takes the share in plaintext. Whatever relays the APDUs sees every share, and that relay is the UCM server.
* The bridge generated the DKEK in Python and rebuilt Shamir shares in process memory. The server held the full DKEK, and the wrapped root blob is in the UCM database.
* Shares were stored in EF `CF01`. Prefix `0xCF` is OpenSC's `DATA_PREFIX`, a readable data object that needs no PIN.
* A connected "card" was never checked for genuineness (no device certificate validation), so a card emulator could take any slot. As the assembly slot it would receive every share.
* `write:hsm` operators saw every custodian's connect URL and typed every PIN, so one administrator could fill every slot.
* Wipe deleted the key but left the DKEK on the assembly card.

These are properties of the protocol, not bugs in the code. The new design changes the trust model so that **keyholders send approvals across the network, never key material**.

## 3. Design principles

1. **The root key never leaves one HSM.** It is generated inside the root SmartCard-HSM and is never exported, wrapped, or reassembled.
2. **Quorum is enforced by the HSM, not by UCM.** The HSM's built-in *public key authentication* (PKA) requires `n` of `m` registered keyholder keys to authenticate before any key can be used. PKA replaces the user PIN. CardContact designed it to work with remote keyholders.
3. **Keyholder credentials are hardware-attested.** Each keyholder key is generated in the keyholder's own SmartCard-HSM. At registration the root HSM checks the key's CV certificate chain on-card (`PSO VERIFY CERTIFICATE`): key → device certificate (`C_DevAut`) → device issuer CA (DICA) → CardContact scheme root CA (SRCA, embedded in the chip).
4. **The server is an untrusted relay.** Challenges, signatures, status words, and public data are the only things that pass through UCM. A compromised UCM can deny service, or misuse an already unlocked window (see section 9). It cannot obtain a secret or forge a keyholder.
5. **PINs are entered only where the card is.** A keyholder's PIN goes to their own card on their own machine. The root HSM's setup PINs are entered at the HSM site, into the local tool, during setup.
6. **Intent is explicit and recorded.** Each keyholder signs the ceremony manifest (what the window may do) with the same hardware key. Every signature the root makes is entered in a hash-chained transcript, which keyholders can countersign after the window.
7. **Fail closed.** No TLS, no device pin, quorum not reached, manifest budget exhausted, bridge unreachable: the operation is refused.

## 4. Threat model

| Adversary | Capability | Outcome under this design |
|---|---|---|
| Network eavesdropper | Reads all RAM and API traffic | Sees challenges, ECDSA signatures, manifests, and status words. None of these is a secret or can be replayed: each challenge is single-use and generated by the HSM. |
| Active network attacker (MITM) | Alters traffic | TLS (required) blocks this. If TLS were bypassed, the short authentication string (SAS) read aloud on the call would not match. A signature over a challenge is accepted only by the root HSM that issued that challenge. |
| Compromised UCM server or administrator | Full control of UCM and bridge | Cannot authenticate without `n` keyholder signatures. Can withhold or relay approvals. Can misuse a window that keyholders have unlocked, limited by the manifest signature budget, and detectable through the transcript and keyholder verification (section 9). |
| Compromised keyholder account (UCM login) | Logs in as the keyholder | Cannot sign without the keyholder's card and PIN. Cannot replace the registered key: registration happens once, at the HSM site, against fingerprints confirmed on a witnessed call. |
| Stolen keyholder card | Physical card | PIN-protected, with the card's retry counter. Alone it is 1 of `n`. |
| Card emulator posing as a keyholder | Software "card" | Registration fails: the root HSM verifies the CardContact chain on-card. |
| Fake root HSM | Software "HSM" presented by the server | The keyholder agent shows the device CHR. Both UCM and the agent pin it at enrollment. The SAS includes it. |
| Colluding keyholders | `n` keyholders working together | Out of scope. This is inherent to any n-of-m control. Choose `n` and the people accordingly. |
| HSM site operator | Physical access to the root HSM | Cannot use keys without the quorum. Can destroy or withhold the HSM, which is mitigated by a backup HSM at a second site (section 6.6). |

Assumptions: TLS private keys on the UCM host are protected. Keyholder workstations are not compromised while the keyholder is approving. The SmartCard-HSM firmware behaves as documented.

## 5. Architecture

```
 Keyholder k (anywhere)                          UCM host                                Root HSM site
 ┌──────────────────────────┐   HTTPS (TLS 1.2+, API key)   ┌───────────────────┐  unix   ┌──────────────┐  RAMOverHTTP/TLS  ┌─────────────────┐
 │ own SmartCard-HSM        │ ────────────────────────────▶ │ UCM API           │ ──────▶ │ RAM bridge   │ ◀───────────────▶ │ ram-client      │
 │  + ucm-keyholder agent   │   challenge ◀── / signature ──▶│ ceremony_service  │ socket  │ (PKA engine, │                   │ root SmartCard- │
 │  PIN entered locally     │                               │ transcript, SAS   │         │  transcript) │                   │ HSM (root key)  │
 └──────────────────────────┘                               └───────────────────┘         └──────────────┘                   └─────────────────┘
          ▲  video call with witness: identity check, SAS read-aloud, manifest walk-through  ▲
```

* **Root HSM**: one SmartCard-HSM initialized with PKA (`m` registered keyholder keys, threshold `n`). It holds the root RSA key as key ID 1. Between ceremonies it is powered off in a safe at the HSM site. The site operator attaches it and runs `ram-client` with the **root slot** URL. That URL is visible only to `write:hsm`, and it alone grants nothing.
* **Keyholder**: has their own SmartCard-HSM with an ECC authentication key, and runs `tools/keyholder/ucm_keyholder.py`. The agent talks only to the UCM API, using the keyholder's own API key. It signs on the local card through OpenSC PKCS#11, and the PIN is typed locally or on a PIN-pad reader.
* **RAM bridge**: relays APDUs to the root HSM. It runs PKA (status, select key, get challenge, external authenticate), key generation, and signing. It also keeps the ceremony transcript and enforces the manifest budget. It never receives a keyholder card's APDUs.
* **UCM**: stores the enrollment exports (public), the pinned root device CHR, the public key, and the closed transcripts. It provides the API the agent and the HSM page use.

## 6. Lifecycle

### 6.1 Keyholder enrollment (once per keyholder)

1. The keyholder generates an EC key on their own SmartCard-HSM (for example `pkcs11-tool --keypairgen --key-type EC:prime256v1 --id 10 --label ucm-keyholder`). The card produces an authenticated request signed by the device key.
2. They run `sc-hsm-tool --export-for-pub-key-auth keyholder.pka --key-reference 10`. The file is public: an authenticated request, `C_DevAut`, and DICA.
3. They upload it with `ucm_keyholder.py enroll keyholder.pka` (or from the HSM page). Only their own custodian row accepts it.
4. UCM parses it. It checks that the key is EC (PKA accepts only ECC keys), that the request's outer CAR matches the device certificate's CHR, and that the device certificate's CAR matches the DICA CHR. It stores the export and shows a **key fingerprint** (SHA-256 of the encoded public point) and the keyholder's device CHR.
5. On a witnessed video call, the keyholder reads their fingerprint from the agent's local output. The witness checks it against UCM. Identity is checked against the keyholder roster.

UCM cannot verify the CardContact chain signatures itself, because the SRCA key is not shipped. The root HSM performs that check at registration, and a forged chain fails there.

### 6.2 Root HSM setup (once, at the HSM site)

Run locally by the site operator, with keyholders and a witness on the call. PINs stay at the site.

```bash
sc-hsm-tool --initialize --so-pin <16 hex> --pin <user pin> \
            --public-key-auth <m> --required-pub-keys <n> [--dkek-shares <k>]   # see 6.6
# UCM HSM page → "Download registration bundle" (one .pka per keyholder, in roster order)
for f in bundle/*.pka; do sc-hsm-tool --register-public-key "$f" --pin <user pin>; done
sc-hsm-tool --public-key-auth-status       # expect total=m, missing=0, required=n
```

`m` cannot change after initialization. Replacing a keyholder means re-initializing the root HSM and restoring the key from backup (6.6). With `n < m`, losing one keyholder card does not block ceremonies.

The first time the root slot connects, UCM reads the HSM's device certificate (EF `2F02`) and asks the operator to pin its CHR. Keyholders confirm the same CHR on the call, and their agents pin it locally (trust on first use, confirmed by a witness).

### 6.3 Root key generation (once)

A normal ceremony (6.4) with the manifest operation `generate_root_key`. Once the quorum has authenticated, the bridge confirms through `ENUMERATE OBJECTS` that key ID 1 does not exist, then sends `GENERATE ASYMMETRIC KEY PAIR` (RSA-2048 or larger, exponent 65537). It parses the public key from the response, and UCM records it as the provider's signing key. Generation is refused if a key already exists. Re-keying is a new root, not an overwrite (section 10).

### 6.4 Routine ceremony

1. **Open.** A `write:hsm` operator opens the window with a **manifest**: the planned operations (for example "publish CRL for Root A", "issue subordinate CA from CSR sha256:…") and `max_signatures`. UCM assigns a `ceremony_id` and computes the canonical manifest hash. Opening a window grants no signing ability.
2. **Attach the HSM.** The site operator connects the root HSM. The bridge reads the device CHR and **refuses to continue** if it differs from the pinned CHR. It reads the PKA status and refuses unless `total = m`, `missing = 0`, `required = n`.
3. **Call.** Keyholders, operator, and witness join a recorded video call. Each keyholder's identity is checked.
4. **Approve (each keyholder, any order, until `n` have done so):**
   1. `ucm_keyholder.py approve --provider <id>` fetches the ceremony. It shows the provider, device CHR (compared with the local pin), manifest, manifest hash, and **SAS**.
   2. The keyholder reads the SAS aloud. The operator's ceremony panel shows the SAS UCM computed. They must match.
   3. The keyholder types `APPROVE` and enters their PIN, which goes to their local card only.
   4. The agent signs the manifest approval: `"UCM-PKA-MANIFEST-APPROVAL-v1\0" ‖ SHA-256(manifest)`.
   5. The agent requests a challenge. The bridge sends `MSE SET AT` (select that keyholder's key by CHR) and `GET CHALLENGE` (8 bytes), and returns the challenge plus the device ID.
   6. The agent signs `device_id ‖ challenge` and submits both signatures.
   7. UCM verifies both signatures against the enrolled key. The bridge checks that the challenge is the one outstanding for that keyholder and unexpired, then sends `EXTERNAL AUTHENTICATE`. The HSM is the final authority. UCM's check catches errors early and keeps the record.
5. **Use.** When the HSM reports `authenticated ≥ n`, the window is unlocked. UCM operator actions (CRL, revocation, subordinate issuance) sign through the bridge. Each signature uses one unit of `max_signatures` and is appended to the transcript as the SHA-256 of the signed bytes plus the operation label.
6. **Close.** UCM regenerates the CRLs of the bound CAs. The bridge then **resets the card** (PKA state is cleared on reset or power-off), reads the status, and confirms `authenticated = 0`. The site operator powers off the HSM and returns it to the safe.
7. **Record.** The bridge seals the transcript. UCM stores it and writes the final hash to the audit log. Each keyholder runs `ucm_keyholder.py transcript --provider <id>`, which checks the hash chain and lists every signature. The keyholder can verify outputs, for example by checking that a published CRL's signature is over a listed hash. Then they countersign `"UCM-PKA-TRANSCRIPT-v1\0" ‖ final_hash`.

### 6.5 Signing with an expired or wrong manifest

The bridge refuses to sign:

* once `max_signatures` is used up;
* after the manifest's `expires_at`;
* when the HSM no longer reports a quorum (for example after a reset);
* for a provider other than the one the window was opened for.

### 6.6 Backup and disaster recovery

Routine ceremonies never move key material. Backup is the one place it must move, and it should be rare and deliberate. The options, best first:

1. **Clone at genesis, in person, once.** Initialize the root and a backup HSM with the same DKEK, created with `sc-hsm-tool --create-dkek-share` (password-protected files, or `--pwd-shares-threshold`/`--pwd-shares-total` to split the password among keyholders). Generate the key on the root, wrap it, and import it into the backup. Store the backup HSM at a second site. One trip, once.
2. **Ship HSMs, not shares.** Send devices in tamper-evident bags by separate couriers, and import locally with witnesses on video.
3. **Remote share import, only over secure messaging.** The SmartCard-HSM supports a device-authenticated secure channel (`openSecureChannel` in the CardContact tooling). A share import that runs inside a channel ending at the keyholder's endpoint would keep shares from the relay. This is not implemented, and it must not fall back to plaintext.

UCM's legacy share mode is not a backup mechanism and stays disabled by default (section 10).

A UCM backup carries the provider's configuration and its keyholder roster (`hsm_custodians`): the slot, the user and the public key each keyholder enrolled, which is what the root HSM was registered with. It does not carry the per-window connect token, a bearer credential; a restore issues a new one for a keyholder it creates and leaves an existing keyholder's token alone. Nothing in a UCM backup can authenticate to the root HSM: that still takes n keyholder cards.

## 7. Keyholder identity and attestation controls

| Layer | Control | Evidence kept |
|---|---|---|
| Hardware genuineness | The root HSM verifies the keyholder key's CVC chain to CardContact SRCA at registration | Registration bundle, PKA status after setup |
| Possession | ECDSA signature over an HSM-issued, single-use 8-byte challenge | Transcript: keyholder, key fingerprint, time |
| Knowledge | Card PIN entered locally (PIN-pad reader recommended) | — (never leaves the card) |
| Account | UCM login / API key bound to the custodian row, with MFA (WebAuthn recommended) for the UCM account | Audit log |
| Person | Recorded video call; ID checked by an independent witness against the roster | Recording, witness statement |
| Channel binding | SAS = `SHA-256("UCM-PKA-SAS-v1\0" ‖ ceremony_id ‖ manifest_hash ‖ device_chr ‖ tls_spki_sha256)`, shown as `NNN-NNN` and read aloud | Transcript records the SAS |
| Intent | Manifest approval signature from each keyholder | Transcript |
| After the fact | Hash-chained transcript; keyholder countersignatures | Stored transcript, audit log entry with final hash |

The SAS includes the SHA-256 of the server TLS certificate's SubjectPublicKeyInfo, as the agent saw it. If a TLS-intercepting proxy sits in front of a keyholder, that keyholder's SAS differs from the operator's. Behind a reverse proxy, set `UCM_PUBLIC_TLS_SPKI_SHA256` to the proxy certificate's SPKI hash so both sides use the same input.

The keyholder agent is the one piece of software a keyholder has to trust: it shows the plan they approve and the SAS they read aloud, and it drives their card. A keyholder must not fetch it from the UCM server they are about to authenticate to, since whoever controls that server could serve an agent that shows one plan and signs another. Distribute it from the source repository at a tagged release, and publish its SHA-256 through a channel UCM does not control (the ceremony invitation, the enrollment call). `ucm_keyholder.py --version` prints the agent's own SHA-256 so each keyholder can read it aloud and compare it on the call.

## 8. Protocol details

### 8.1 APDUs

| Step | APDU | Source / confidence |
|---|---|---|
| PKA status | `80 54 00 00 04` → `total, missing, required, authenticated` | OpenSC `sc_hsm_public_key_auth_status` (confirmed) |
| Initialize with PKA | tag `93 02 <m> <n>` in `INITIALIZE DEVICE` data | OpenSC `sc_hsm_initialize` (confirmed); used by `sc-hsm-tool` at the site |
| Register key | `00 22 81 B6 83 <CHR or CAR>` + `00 2A 00 BE <CVC>` for DICA then device; `00 22 81 B6 83 <outer CAR>`; `80 54 00 00 <authenticated request>` | OpenSC `sc_hsm_register_public_key` (confirmed); run by `sc-hsm-tool` at the site |
| Select key for authentication | `00 22 81 A4 <83 L CHR>` | OpenSCDP `selectPubKeyForAuthentication` ("MSE for External Authenticate"); P1/P2 are the ISO 7816-8 SET AT values. **Hardware check required.** |
| Challenge | `00 84 00 00 08` | OpenSCDP: "obtain an 8 byte challenge" (confirmed length) |
| External authenticate | `00 82 00 00 <signature>` | OpenSCDP `externalAuthenticate(signature)`. Signature over `device_id ‖ challenge`; device id taken from the device certificate CHR (confirmed). Encoding of the signature (plain `r‖s`) and of `device_id` (CHR value bytes): **hardware check required**; both are configurable. |
| Device certificate | `SELECT 2F02`, odd-INS `READ BINARY` loop | Matches existing share-EF code; `2F02` is `C_DevAut` + DICA (confirmed) |
| List objects | `80 58 00 00 00` | OpenSC `sc_hsm_list_files`. **Hardware check required.** |
| Generate RSA key | `00 46 <key id> 00` with `5F29 01 00 ‖ 42 "UTCA00001" ‖ 7F49{06 <0.4.0.127.0.7.2.2.2.1.2> ‖ 82 01 00 01 ‖ 02 <bits>} ‖ 5F20 <CHR>` | OpenSC `sc_hsm_encode_gakp_rsa` + `encode_cvc` (confirmed order and tags; CPI 0 assumed) |
| Sign | `80 68 <key id> 30 <DigestInfo>` (extended length) | OpenSC: `ALGO_RSA_PKCS1 = 0x30`, "DigestInfo input and PKCS#1 V1.5 padding" (confirmed) |

Every signature from the root HSM is verified against the recorded public key before UCM uses it.

### 8.2 Signed messages

| Purpose | Bytes signed by the keyholder key (ECDSA, hash from the key's CVC OID, default SHA-256) |
|---|---|
| HSM authentication | `device_id ‖ challenge(8)` |
| Manifest approval | `"UCM-PKA-MANIFEST-APPROVAL-v1" ‖ 0x00 ‖ SHA-256(canonical manifest)` |
| Transcript countersignature | `"UCM-PKA-TRANSCRIPT-v1" ‖ 0x00 ‖ final transcript hash` |

The two UCM messages have a fixed ASCII prefix and a NUL, and their lengths differ from the authentication input. So no UCM message can be passed off as an HSM authentication, or the reverse.

The canonical manifest is UTF-8 JSON with sorted keys and `(",", ":")` separators. Fields: `version`, `ceremony_id`, `provider_id`, `provider_name`, `device_chr`, `threshold_n`, `total_m`, `opened_at`, `opened_by`, `expires_at`, `operations[]` (`type`, `label`, optional `ca_id`), `max_signatures`.

### 8.3 Transcript

Each entry is `{seq, at, event, data, prev}`, and `hash = SHA-256(prev ‖ canonical(entry))` with `prev` of entry 0 being 32 zero bytes. Events: `opened`, `device`, `pka_status`, `manifest_approved`, `authenticated`, `unlocked`, `key_generated`, `signed` (label, SHA-256 of the signed bytes, signature SHA-256), `locked`, `sealed`. The bridge holds it during the window. UCM keeps the sealed transcript in the provider record and the audit log.

## 9. Security properties and residual risk

Achieved:

* No secret crosses the network or reaches UCM. Keyholder PINs stay on keyholder cards, setup PINs stay at the HSM site, and the root key stays in the HSM.
* Eavesdroppers learn nothing reusable. Active attackers must defeat TLS and the SAS check.
* Using the key needs `n` hardware-attested keyholder keys, enforced by the HSM. A UCM administrator alone cannot sign.
* Card emulators, wrong devices, and replayed challenges are rejected.

Residual (accepted, mitigated by procedure):

* **Use of an unlocked window.** Once the HSM is unlocked, it signs what the bridge sends. A fully compromised UCM host could sign something not in the manifest, up to `max_signatures`, while the window is open. Mitigations: a small `max_signatures`; short `expires_at`; the transcript records the hash of everything signed; keyholders verify outputs before publication; the site operator ends the window by unplugging the HSM. Only threshold signing (MPC), where every signature needs the quorum, removes this. That is a different architecture (section 11).
* **Single root HSM.** Availability depends on the site and the backup (6.6).
* **Firmware assumptions.** The items marked "hardware check required" in 8.1 must pass the checklist in section 13 before production use.

## 10. Legacy share mode and hardening

* `device_scheme = shares | random | domains` ceremonies (the previous design) are **refused** unless `UCM_ALLOW_LEGACY_SHARE_CEREMONY=1` is set on both UCM and the bridge. The refusal message points to this document. When enabled:
  * wipe now also clears the DKEK on the assembly card;
  * the in-place root re-sign on key roll stays as before, documented as unsafe.
* Bridge hardening, all schemes:
  * The RAM listener refuses to start without a TLS certificate, unless `RAM_BRIDGE_ALLOW_PLAINTEXT=1` (tests and development only). It sets a minimum of TLS 1.2.
  * Fake mode comes from the bridge's own `RAM_BRIDGE_FAKE` only. A control-socket parameter can no longer turn it on.
  * `Content-Length` must be a non-negative integer within the limit.
  * The control socket is created under `umask 0o177`, so it is never briefly world-accessible.
  * Signing checks that the request's provider is the provider of the open window.
  * PKCS#11 signing selects the private key by key ID, not the first key found.
* UCM hardening:
  * A connect URL is shown only to its own custodian. The root slot URL is shown to `write:hsm`.
  * Connect tokens are rotated when a window closes.
  * Root rollover in PKA mode is a **new provider and new root** (issue a cross-certificate if relying parties need continuity). UCM never overwrites an existing root certificate's key.

## 11. Alternatives considered

| Option | Verdict |
|---|---|
| Hardened DKEK share transport (status quo) | Rejected: plaintext shares through the relay is inherent. |
| Commercial network HSM with remote quorum (Entrust nShield Remote Administration, Thales Luna remote PED) | Equivalent model, FIPS 140-3 L3 and familiar to auditors. Recommended where budget allows. UCM already supports PKCS#11 providers. |
| Threshold signing / MPC | Only option that enforces quorum per signature. Key shares usually live outside certified HSMs; threshold RSA is awkward; less familiar to auditors. Possible future work. |
| In-person ceremonies | The gold standard; infeasible here except for a one-time genesis and backup (6.6). |

### 12.1 Implementation status

All phases are implemented on this branch and covered by software tests against `FakePkaRootHsm`, a software root HSM that verifies keyholder signatures:

* `backend/services/hsm/sc_hsm_pka.py`, `backend/services/hsm/pka_engine.py`: protocol module and bridge engine.
* `backend/services/hsm/ram_bridge.py`, `ceremony_service.py`, `api/v2/hsm.py`: bridge integration, hardening, service and API.
* `tools/keyholder/`: keyholder agent.
* `frontend/src/pages/hsm/PkaCeremonyPanel.jsx`: HSM page.
* Tests: `test_sc_hsm_pka.py`, `test_sc_hsm_pka_ceremony.py`, `test_keyholder_agent.py`, `PkaCeremonyPanel.test.jsx`.

Decided during implementation:

* Root HSM initialization and keyholder key registration run locally at the HSM site with `sc-hsm-tool`, from the registration bundle UCM produces. Remote registration would need the root HSM's user PIN to travel through UCM.
* A window whose quorum was never reached can close without a reachable root HSM. Partial authentication grants nothing, and leftover state is cleared the next time the device attaches. A window that was unlocked must be locked with a confirmed reset.
* Provider edits cannot set or change `public_key_pem`, `pinned_device_chr`, `keyholders_locked`, `root_connect_token`, `ceremony_manifest` or `transcripts`.
* Backups include the keyholder roster with public keys and exclude connect tokens (section 6.6).
* The public path `/hsm/ram/` has its own rate limit bucket at the standard rate: one request per APDU round trip, so a ceremony is a burst of machine traffic that must not share the admin API's quota.

Still open:

* The hardware checklist (section 13) has not been run.
* The new UI strings are machine translated in the eight non-English locales and need review by native speakers.
* The design and code need a security review by someone who did not write them.
* The keyholder agent needs a signed release, or a checksum published through a channel UCM does not control (section 7).

## 13. Hardware validation checklist (before production)

Run with a real SmartCard-HSM (firmware ≥ 3.x) as root, and two keyholder cards, in a test 2-of-2 or 2-of-3 setup:

1. `sc-hsm-tool --public-key-auth-status` matches `80 54 00 00` as read through the bridge.
2. The `MSE SET AT` encoding (`00 22 81 A4 83 <CHR>`) is accepted for a registered key: SW `9000`.
3. `EXTERNAL AUTHENTICATE` accepts a plain `r‖s` signature over `CHR-value-bytes ‖ challenge`. If not, set `UCM_PKA_SIGNATURE_FORMAT=der` or `UCM_PKA_DEVICE_ID_FORMAT=chr_tlv` and record the working combination here.
4. After `n` authentications, status shows `authenticated ≥ n`. After a card reset, it shows 0.
5. `ENUMERATE OBJECTS` lists `CC01` after generation and not before.
6. `GENERATE ASYMMETRIC KEY PAIR` returns an authenticated request whose `7F49/81` modulus matches the PKCS#11 view of key ID 1.
7. `SIGN` with algorithm `0x30` over a DigestInfo verifies under that public key.
8. A replayed signature (same challenge twice) is rejected by the card.
9. A keyholder export from a card not registered on this HSM is rejected at `MSE SET AT` or `EXTERNAL AUTHENTICATE`.
